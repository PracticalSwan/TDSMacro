# Project instructions — TDS Macro

- Read README.md, docs/development.md, docs/setup.md and docs/verification.md before implementation. Inspect actual status and nearby instructions. Preserve unrelated and ignored user work.
- Keep the Python/Tk app small: one supported strategy, global F1 start/F2 stop, responsive GUI, separate guarded worker, stop on close. No services or auto-updates.
- Never invoke Codex CLI. Never use injection, executors, client memory/session/cookie access, modified clients, anti-cheat bypass, anti-idle or auto-refocus. No credentials are needed.
- Computer-use tools (including CUA/`cua_repl`, `@oai/sky`, and browser-act desktop control) may be used for ordinary project work and preparatory UI/setup while no macro run is active. They must not be used to perform, verify, or calibrate macro actions. Before an explicit F1 start or any live macro run, close all computer-use sessions/surfaces and overlays across agents, then re-verify the supported Roblox window identity, foreground, geometry/DPI, and a clean native capture. From macro start until its worker stops or exits, no agent may use or attempt computer-use, activate windows, or calibrate from control-session overlays; live verification uses only the project's guarded Windows input and native capture path. If computer-use starts or affects the Roblox client during a run, stop the worker through the guarded F2 path, preserve evidence, and require a fresh verified session before resuming.
- Input requires an explicitly started run and verified foreground identity/geometry/DPI. Reuse control.py guards and release cleanup. Preserve F2/F8/Escape and stop markers inside waits/holds. Never overlap controllers.
- After one map-vote E and the S backstep, re-read a missing complete target title while stationary for at most two seconds, checking stop/foreground and map-vote state on every capture. Never repeat E. Ready requires the unique intended Dead Ahead title and an exact vote badge of 1; one unreadable badge may get one D view-clear only with current map-vote state and `voting_floor(..., for_strafe=True)`, followed by a fresh title/count read. VIP still needs the E keycap plus literal Override Map and two stable reads; keep the 12-D cap.
- Preserve map/title/vote, overhead pose, actual cash/price, tower name/level/count and result checks. Detect results before spending. Never repeat uncertain placement/purchase clicks. One selection-only retry requires two positive hover checks and unchanged count.
- Play Again may return to map_vote: select/vote and set a fresh camera. Direct match_ready restarts verify zero towers and retained pose without repeated movement. Establish four physical boards; never guess an index.
- Voting-room movement requires two-sided stone support before board strafing; one-sided edge support permits forward correction only, and losing both supports stops. Approach VIP on its actual Override Map prompt, not a fixed strafe into the machine. Preserve these checkpoints when decorations or camera views change.
- An explicitly started continuous GUI run defaults to bounded failure recovery. Game failures or a verified natural foreground return can reopen TDS. Focus loss releases input immediately; wait passively at most five seconds for the same original client/geometry/DPI, confirmed twice, before fresh-session recovery. Never reclaim focus or resume interrupted spending. Manual stop/pause, persistent focus loss, identity/geometry changes and setup/storage errors cancel. Retain the original client anchor through close cooldown; close only that verified client and recognized confirmation. The calibrated Roblox disconnect modal requires exact `Disconnected`, `Leave`, and `Reconnect` labels, rechecked before one guarded Leave click. If the same foreground client reaches Roblox Home, require all four exact Home-navigation anchors in two reads before one additional ordinary WM_CLOSE; an exact app-close confirmation may be handled through its existing guarded click. Never repeat Leave. Process exit is still required before the official URI; unknown screens or unclosed clients stop without force termination. Verify a stable new lobby before binding a fresh driver. Keep one worker, shared root stop controls and separate attempt evidence; three relaunches without a win exhaust the limit.
- Baseline: English TDS Store GDK, physical 1920×991/120 DPI, Solo Survival/Easy Dead Ahead, Golden Scout only slot 1, nine vertical Scouts/44 actions. Other geometry needs independent calibration/live proof, not proportional clicks. Modifiers change income; skins cannot define identity.
- Use CodeGraph for structural discovery when .codegraph exists, then targeted reads for stale/non-symbol data. Actual source/runtime remain authoritative.
- **Real-game trial-and-error is the primary acceptance for gameplay/navigation changes.** Reproduce a recorded failure, run a narrow offline regression, implement the minimum fix, and then test the actual macro in foreground Roblox at the earliest safe opportunity. Treat real captures, transitions, wins, rewards and recovery outcomes as authoritative; do not loop over generic unit-test edits, synthetic fixtures or redundant full suites instead of exercising the changed behavior in game. Usually run focused tests per change and one complete suite before integration/release; another full suite is justified only by a subsequent material code change. If live input is blocked (foreground/identity/another worker), do not steal focus: report the specific blocker and hand off an exact supervised trial, rather than inventing success or creating tests indefinitely. Keep cosmetic checks proportional and record every unverified live gate.
- **Optimize measured hot paths when safe:** profile actual screen capture, OCR/template scans, status/PNG writes, lobby transitions and memory allocation; prefer smaller verified regions, bounded caching and fewer redundant operations. Retain identical map/tower/vote/cash/pose/result recognition thresholds and cancellation checks. Compare identical real-frame inputs before/after, verify outputs and measure CPU, elapsed processing and storage. A 20ms image-processing gain does not imply a faster 7-minute server-paced match. Avoid speculative infrastructure, extra processes/dependencies or reducing safety waits merely to improve a benchmark. Update CHANGELOG.md and verification docs for material changes.
