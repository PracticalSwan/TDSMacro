## Goal and evidence

When selecting Hardcore Gems + Tower XP — Slot 4 / Solo in the TDS Macro dashboard, the user explicitly chooses a supported tower variant for slot 4 from a small verified catalog. The macro uses that tower's validated purchase profile instead of discovering an arbitrary eligible tower and repeatedly reading its price to decide whether to attempt X1. A selected tower is a preference, not a guarantee of placement or earned XP. Core Gem defense remains the priority.

## Minimal GUI behavior

- Show a read-only **Slot 4 tower** dropdown only when Hardcore Gems + Tower XP is selected. The initial intended choices are Juggernaut and Golden Scout after their profile acceptance gates; show only fully qualified profiles as selectable in production. Unqualified entries belong in developer records, not a misleading usable list.
- Display observed/validated base cost, expected role (optional XP), required perk, and a short affordability note. Loadout summary must show the exact selected variant in slot 4, Boomerang / regular Crook Boss / Farm in slots 1–3 and empty slot 5.
- Persist only the selected stable profile ID as a preference; validate it when loading. Require an explicit choice if no valid saved selection exists. Disable edits during an active run; a change is applied only at the next explicitly started run or an authorized verified rotation boundary.
- Selection is not equip authorization. In single-strategy mode, require manually equipped matching tower/perk unless the independently verified [loadout switching](2026-11-23-v1.0-loadout-switching.md) flow has passed its acceptance gate. Missing ownership, wrong perk, wrong slot or unsupported profile blocks Start/preflight with actionable correction; no silent substitute.
- Existing Golden 9/10 and Hardcore 3 selectors and equipment rules are unchanged. Do not create one duplicated strategy per optional tower, a new UI framework, or another background controller.

## Tower-specific profile and purchase decision

Use one small explicit data registry consumed by GUI, preflight, worker and rotation. No free-text tower names, arbitrary executable config, untrusted wiki prices or runtime inference from cost. Each entry should include stable ID, canonical name, variant/perk, slot=4, level=0, validated expected base quote, exact approved X1 point/footprint (currently (976,580), requalify if different), placement prerequisites/window, supported settings, evidence status/reference and profile revision. Account inventory ownership and game/UI compatibility must be verified separately. A tower cannot duplicate core identities or use an unsupported placement type. Current OPTIONAL_EXP_TOWERS is an OCR allowlist, not a verified catalog.

Illustrative profile IDs (not current code): juggernaut, golden_scout, scout, minigunner. Only entries passing acceptance are enabled. A profile revision is pinned for each run/rotation leg; stale or unknown selections must not fall back to another tower.

**Recommended OCR reduction:** use the validated profile price and existing deterministic critical-defense milestones to plan the X1 purchase window and budget. Do not continuously rediscover the slot-4 tower or independently OCR its price on every optional scheduling poll. Reuse the already-read shared HUD cash and the existing next-core quote. Verify the actual matching identity, perk, live price and affordability at preflight and immediately before the one paid placement. Where the live price differs, is unreadable, or the profile is stale, defer/skip X1 or stop for setup correction as appropriate; do not guess or accept a new quote automatically. Keep live cash and reserve checks at the transaction boundary (cash >= validated price + next verified core reserve), existing camera/terrain, valid preview, fresh input guard, and positive postcondition. No fixed wave or expected income authorizes spending. A cheaper preselected profile improves affordability but does not prove a safe purchase.

If a later implementation can replace a cash OCR observation with an independently validated equally reliable in-game signal, test that separately; a green/affordable icon alone cannot prove the protected core reserve. No blanket removal of cash OCR, upgrade OCR, receipt OCR or other safety checks is in scope. No change to the v0.5.2 runtime now.

## Integration and accounting

- Existing app.py STRATEGIES and Dashboard._strategy_changed / Controller.start: add the conditional selector, summary, and validated immutable choice in the worker launch/config. Reject unknown selection and incompatible non-XP choice.
- Existing session.py Hardcore hotbar preflight: match actual ordered loadout to the selected profile (including verified perk); do not infer selection from an OCR caption. Preserve the current three-tower branch and verify fresh state after direct restart/relaunch. Actual slot verification remains mandatory.
- Existing hardcore_match.py HardcoreMatchV2: use the approved profile for X1 while keeping the existing core plan, optional budget/reserve, one guarded placement and positive count/name/level proof. Consolidate duplicated optional-price reads only after focused safety regression. No new engine.
- Existing loadout.py recognizers: extend only for exact approved tower/variant and native evidence. Any unsupported name, perk, price or placement geometry must not authorize a click.
- Existing rotation plan: each Hardcore XP leg stores exact selected slot-4 profile ID/revision and expected preset/ordered loadout. Switching only slot 4 still requires full readback, including perk and empty slot 5. No blind reuse of a preset name or mid-match changes.
- Existing result/diagnostic ledger: report requested tower, verified tower, profile revision, expected/verified price, core reserve, placement status and reason. Distinguish credited Gem cycles, optional placements and positive tower-specific XP proof. For a Gem-only quota the qualifying result counts when X1 is deferred; XP-target quotas require positive actual XP evidence and selected variant (not merely placement). Use the existing bounded recovery rules and one worker.
