## Target behavior

User configures a list of strategy legs, each with a positive integer **successful-run quota**, plus **Repeat loop**. Example:

| Order | Exact selectable variant | Count verified successful runs |
| --- | --- | --- |
| 1 | Golden Scout — **10 Max** / Dead Ahead / Easy | **5** |
| 2 | Hardcore Gem Grind — **3 Towers** / Solo | **5** |
| Loop | Return to leg 1 after leg 2 is complete | repeat until explicit user stop or a safety stop |

This means G x5 **verified successes** → return to lobby → verified loadout switch → H x5 **verified successes** → return to lobby → verified switch → repeat. One early defeat, disconnect, failed/ambiguous placement or recovery is **not one of the five successes**. The user can instead select Golden 9 or Hardcore XP 4, but those have distinct success predicates. The GUI must name the exact Golden profile, not just `golden_scout`.

## Success predicates and accounting

| Variant | Required v1.0 success event | Not enough |
| --- | --- | --- |
| Golden Scout 10 | Independently verified **wave-20 Easy Solo Dead Ahead Victory**, readable Coin result, and **50/50 intended actions + 10 level-4 Scouts** | Entering a match, 10 placements only, banner only, unreadable reward, partial action list |
| Golden Scout 9 | Same full Easy wave-20 verified Victory and Coin result, with **44/44 actions**, first eight Scouts L4 and ninth L3 | Any other Golden profile's success or early/unknown result |
| Hardcore Gem 3 | Independently verified **wave-30 natural Defeat** on Wretched Front Solo Hardcore, **137 Gems displayed**, target-wave & **75/75 core actions/final levels** verified | Early Defeat, fewer than 75, unverified reward, recovery, partial run |
| Hardcore Gem+XP 4 | At minimum a verified **Gem** result at wave30/137; if the quota objective is **Gem + Tower XP**, additionally require **confirmed X1 placement plus positive tower-specific XP reward evidence** | The current `xp_placement_cycles` count alone, or a Gem cycle with no optional tower |

**Current code note:** `Session.play_matches` updates `wins` for status `victory` and reads coins after the result. `Session.play_hardcore_v2` increments `gem_cycles` only for `result_verified` with 137 displayed Gems. These counters are **not themselves a durable, exact-once, cross-strategy rotation journal**; the XP placement counter is not a numerical XP reward confirmation. v1.0 must validate the more specific predicates above, not equate `attempts`, `matches_completed`, `wins`, and `gem_cycles`.

## Proposed minimal durable workflow

Use **one** supervising controller/worker path, with a small ordered plan and explicit strategy transition. Reuse the existing gameplay engines; do not create a second input driver or a permanent background service.

```text
User starts rotation
  -> Verify currently selected strategy and loadout
  -> Play one guarded match
  -> Read + persist exact result / unique match ID
  -> IF valid success: increase current leg successes by one
  -> IF leg quota not met: guarded same-strategy replay
  -> IF leg quota met: stop same-strategy replay at result boundary
      -> guarded Return to Lobby
      -> verified preset loadout switch (or manual gate)
      -> strict next-strategy preflight, map/mode/camera
      -> continue with next leg
  -> IF final leg met and Repeat=ON: next loop, first leg
  -> IF Repeat=OFF: stop at verified result/lobby, show completed
  -> On stop/failure: no further game input until safe user action
```

### Proposed configuration (illustrative, NOT a current executable file)

```json
{
  "rotation_version": 1,
  "legs": [
    {"strategy_key": "golden_scout_ten", "successful_runs": 5},
    {"strategy_key": "hardcore_gems_three", "successful_runs": 5}
  ],
  "repeat": true,
  "stop_on_unverified_result": true
}
```

Define a **strategy_key** distinct from current `golden_scout` runtime ID; bind Golden 9/10 to different immutable profile hashes and Hardcore 3/4 to their distinct strategy IDs. Validate unknown/duplicate keys, empty legs, numeric range (proposed **1–100** per leg), persistent plan hash, profile digest and mode-specific success predicates before starting. For a Hardcore Gem+XP leg, require the exact [selected slot-4 profile ID and revision](2026-11-25-v1.0-slot4-tower-selection.md), expected ordered loadout/perk, and explicit Gem-only vs actual-XP quota objective. The five intended slot-4 choices are Juggernaut, Golden Scout, Operator, Enforcer and Kingpin; only individually qualified profiles may enter a rotation leg. These are part of the configuration hash and immutable match/leg identity. No silent substitute, free-form tower ID, or mid-match changes. No runtime arbitrary script/code execution or remote scheduler is needed.

## Crash-safe counters and recovery

- Maintain one append-only session ledger with: `rotation_id`, configuration hash, `loop_index`, `leg_index`, `strategy_key`, `attempt_id`, `match_id`, `result_evidence_ref`, `result_status`, `success_credited`, `cumulative_successes`, `switch_status` and timestamp. Use local atomic writes/rename for the current state; keep private captures outside Git.
- Credit each uniquely identified match **at most once** after verified result and durable evidence. If the GUI/worker restarts after a crash, reconcile the ledger rather than guessing from the status snapshot or counting a screenshot twice.
- Before every match and every loadout switch, re-check the current plan, selected profile hash and process ownership. If a prior result is durable but the lobby/selected loadout is not verified, resume in a **paused / needs verification** state, not with blind input.
- A manual F2/F8/Escape stops immediately using existing guards, even with an unfinished quota. Provide a separate **Stop after this verified match** user action for graceful queue exit. Do not reinterpret F2 as “finish match” or let the queue silently restart after app reopen.
- Reuse the released **two verified direct replays and three guarded recovery relaunches** per streak without credit. Preserve streak accounting across a leg, reset only after genuine credited success, and stop on protected conditions or an exhausted budget.
- Distinguish: **attempts**, **successful runs**, **failed/early results**, **recoveries**, **skipped XP placements**, **displayed rewards**, and **current leg progress** in GUI and logs.

## User interface plan (Tk; opt-in)

Use current dashboard conventions, avoid a new framework. Add a compact **Rotation** mode beside single strategy:

- Ordered leg rows: strategy dropdown, conditional verified slot-4 tower dropdown for Hardcore Gem+XP, quota objective, positive integer **successful runs**, remove/reorder, and optional `Repeat loop` toggle. Default remains **single strategy**, with rotation OFF.
- Preview each leg's loadout and eligibility warnings before Start, linking to the relevant requirements sheet; hard-block invalid known configurations such as four-Farm opening cash below $1,200 if observed.
- Live display: `Golden Scout 3/5 verified → Hardcore 0/5 queued`, loop number, attempted games, credited wins/Gem cycles, last result and current phase `Playing | Returning to lobby | Switching preset | Verifying | Needs user action | Stopped`.
- Require explicit user authorization to start; do not auto-start rotation on reboot, automatic update, crash recovery or an idle GUI.
- If automatic loadout switching cannot prove slot identities, **pause at lobby and request manual change**. The banner must truthfully say rotation is waiting, never “running unattended.”

## Version roadmap and release gates

- **v0.5.2 is the installed stable version**. This planning-only task creates documents, not a feature build, migration, updater change, gameplay test, tag or publication.
- Fixes/new independent features before v1.0 use conventional interim versions **v0.5.3, v0.6.0, v0.7.0, etc.**, each with its own acceptance and release. No immediate version jump and no requirement to reserve every intermediate version.
- **v1.0.0** is the intended milestone for truly verified strategy requirements, safe automatic loadout switching, exact quota-based successful-run rotation, resilient recovery, usable GUI and completed native multi-cycle acceptance. If the preset UI cannot be safely verified, unattended rotation must be deferred, not represented as complete.
- Maintain old single-strategy Golden 9/10 and Hardcore 3/4 modes, existing dynamic cash/price guards, protected route hashes and emergency-stop semantics throughout the transition.
